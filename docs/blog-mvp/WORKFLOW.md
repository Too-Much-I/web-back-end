# 블로그 MVP 단계별 작업 흐름

블로그 MVP는 아래 Phase를 번호 순서대로 한 번에 하나씩 진행한다. 선행 Phase가 `DONE`이 아니면 다음 Phase를 시작할 수 없다.

## 상태 값

단계 상태는 다음 값만 사용한다.

- `TODO`: 아직 계획을 시작하지 않음
- `PLANNING`: 저장소 분석과 계획서 작성 중
- `AWAITING_APPROVAL`: 계획서가 `DRAFT`이며 사용자 승인을 기다리는 중
- `IN_PROGRESS`: 사용자 승인 후 승인된 범위를 구현 중
- `BLOCKED`: 요구사항 충돌, 사용자 변경, 환경 문제 등으로 진행 중단
- `VERIFYING`: 구현을 끝내고 테스트 및 Codex review 중
- `DONE`: 승인 범위 구현과 필수 검증을 모두 통과함

이 외의 상태를 만들거나 둘 이상의 단계를 동시에 `IN_PROGRESS`로 표시하지 않는다.

## 단계

| Phase | 이름 | 핵심 범위 |
|---|---|---|
| 00 | Agent guardrails 및 저장소 분석 | 관리 문서, Codex 정책, 안전 스크립트, 현재 상태 분석 |
| 01 | Java 21, 테스트, Mongo 스캔, Scheduling, 로컬 환경 | 구현 기반과 로컬 검증 환경 |
| 02 | 게시글 목록·상세·제목 검색 | 공개 게시글 읽기 API |
| 03 | 익명 댓글과 번호 기반 validation | 익명 작성·조회와 고정 규칙 1~10 |
| 04 | 댓글 rate limit과 숨김·복원 | 남용 방지와 내부 운영 처리 |
| 05 | 뉴스레터 구독과 구독 해지 | 즉시 ACTIVE, 멱등 구독, 해지 |
| 06 | 뉴스레터 15분 자동 발송 | 예약, 중복 방지, 재시도, kill switch |
| 07 | 내부 운영 API와 보안 | `/internal/**` API Key 인증과 운영 기능 |
| 08 | 전체 회귀 테스트와 API 문서 | 전체 요구사항 검증과 문서화 |

## 단계 진행 순서

각 단계는 반드시 다음 순서로 진행한다.

```text
PLAN
→ 사용자 승인
→ IN_PROGRESS
→ 테스트
→ Codex review
→ DONE
```

세부 상태 전이는 다음과 같다.

1. `TODO`에서 `PLANNING`으로 변경하고 읽기 전용 분석을 수행한다.
2. `PLANS.md` 형식의 계획서를 `DRAFT`로 작성한다.
3. 단계 상태를 `AWAITING_APPROVAL`로 변경하고 사용자에게 승인을 요청한다.
4. 사용자가 명시적으로 승인한 경우에만 계획을 `APPROVED`, 단계를 `IN_PROGRESS`로 변경한다.
5. 현재 단계의 승인 범위만 구현한다.
6. 구현 후 단계를 `VERIFYING`으로 변경하고 관련 테스트와 `./gradlew clean test bootJar`, `git diff --check`를 실행한다.
7. Codex review에서 요구사항, 제외 범위, 승인 계획, 변경 파일을 대조한다.
8. 모든 검증이 성공한 경우에만 계획을 `EXECUTED`, 단계를 `DONE`으로 변경한다.

## 중단 조건

- 테스트가 실패하면 `DONE`으로 변경할 수 없다.
- 요구사항과 구현이 다르면 임의로 판단하지 않고 중단한다.
- 승인된 계획 밖의 변경이 필요하면 소스 수정을 중단하고 보고한다.
- Codex가 만들지 않은 작업 트리 변경이 발견되면 중단하고 보고한다.
- 현재 브랜치가 `feat/blog-mvp`가 아니면 구현을 시작하지 않는다.
- 문서 충돌이나 요구사항 해석의 복수 선택지가 있으면 사용자 결정을 기다린다.

중단 시 상태를 `BLOCKED` 또는 실제 상황에 맞는 미완료 상태로 유지하고 `IMPLEMENTATION_STATUS.md`의 열린 문제와 Session Log에 원인을 추가한다. 실패 기록을 삭제하거나 성공으로 바꾸지 않는다.

## 단계 완료 보고

각 단계 종료 보고에는 다음을 포함한다.

- 승인된 목표와 실제 구현 범위
- 변경 파일
- 실행 명령과 테스트 결과
- Codex review 결과
- 요구사항 또는 계획과의 차이
- 남은 위험과 열린 문제
- 다음 단계 시작 전에 필요한 사용자 행동
